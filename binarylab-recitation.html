Recitation: Binary Mystery & Buffer Overflow

In this recitation you will practice reading x86-64 programs at runtime with gdb. You will inspect three short “mystery” functions and a program with a classic stack buffer overflow, and answer questions on Gradescope. Everything runs in a GitHub Codespace (an x86-64 Linux machine in the cloud), so the given binaries run natively and gdb works fully.

  • 1. Set up your environment
  • 2. A quick gdb refresher
  • 3. The mystery functions (Q1–Q7)
  • 4. The buffer overflow (Q8–Q10)
  • 5. Writing and reading binary files

1. Set up your environment

Fork the examples repository
  1. Log into github.com and open nyu-cso-fa26/binarylab-examples.
  2. Click the Fork button (top-right) and create a fork under your own account. You now have your own copy at https://github.com/<your-username>/binarylab-examples.
Start a Codespace on your fork
  1. On your fork, click the green Code button, select the Codespaces tab, and click Create codespace on main. The first time, it takes a minute or two.
  2. A VS Code window opens in your browser with a terminal at the bottom (open one with Terminal → New Terminal if needed). Confirm you are on an x86-64 machine with uname -m, which should print x86_64.

The default codespace image already has gcc, make, gdb and objdump installed — nothing to install.

One-time gdb setup

The repository ships a .gdbinit file (it turns on a nicer disassembly display and silences the debuginfod prompt). By default gdb refuses to load a .gdbinit from a project directory for security. Allow it by running this once in the terminal:

echo "set auto-load safe-path /" >> ~/.gdbinit

After this, starting gdb in the repository will automatically load its .gdbinit. (You can check it worked: gdb should not ask about debuginfod, and show disassemble-next-line should print on.)

Build the programs
make

This builds mystery, mystery-sol, and exampleoverflow. You will use mystery-sol for Q1–Q7 and exampleoverflow for Q8–Q10.

2. A quick gdb refresher

Start the debugger on a program with gdb ./mystery-sol. Useful commands:

break func            set a breakpoint at the start of a function (e.g. break mystery1)
run                     start the program; it stops at the next breakpoint
continue  (or c)        resume until the next breakpoint
nexti     (or ni)       execute one machine instruction (step over calls)
stepi     (or si)       execute one machine instruction (step into calls)
finish                  run until the current function returns, print its return value

info registers r      show one register, e.g. info registers rsi
print $rsi  (or p)      same thing as an expression; p/x $rsi prints it in hex

x/10dw $rdi             examine memory: 10 decimal 4-byte words at the address in %rdi
x/s   $rdi              examine memory as a C string
x/gx  $rsp              examine one 8-byte value (giant, hex) at the stack pointer

disas func           disassemble a function, e.g. disas get_input
quit      (or q)        leave gdb

Recall the x86-64 calling convention: the first integer/pointer arguments are passed in %rdi, %rsi, %rdx, %rcx, … (use the 32-bit names %edi, %esi, … for int arguments), and a function returns its value in %rax (%eax for int).

3. The mystery functions (Q1–Q7)

Run gdb ./mystery-sol. Using the commands above, set a breakpoint at mystery1, mystery2, and mystery3, run the program, and inspect the arguments (in the registers), the memory they point to, and the return values. From that, work out what each function computes.

Answer Q1–Q7 as you go.

4. The buffer overflow (Q8–Q10)

Now look at exampleoverflow, whose source is in the file exampleoverflow.c:

bool get_input()
{
    char buf[8];
    gets(buf);                               /* NO bounds checking! */
    return strcmp(buf, "supersecret") == 0;
}

void give_out_lots_of_money()
{
    printf("Congratulations! You have earned lots of $$$\n");
    exit(0);
}

int main()
{
    if (get_input())
        give_out_lots_of_money();
    else
        printf("sorry dude, you don't have the right password\n");
    return 0;
}

gets() reads a whole line into buf without checking its length. buf is only 8 bytes, so a longer line runs off the end of buf and keeps writing up the stack, over get_input's saved return address. By putting the right bytes there, you can make get_input “return” straight into give_out_lots_of_money() — without ever knowing the password.

Use gdb to answer Q8–Q10:

  • Q8 — the address of give_out_lots_of_money (the function you want to jump to): info address give_out_lots_of_money.
  • Q9 — how many bytes of input sit between the start of buf and the saved return address: read it off disas get_input.
  • Q10 — set a breakpoint at get_input's ret, type a long run of A's, and examine the saved return address with x/gx $rsp to see that you really did overwrite it.

5. Writing and reading binary files

Answering Q8–Q10 only requires reading the program with gdb. But to actually carry out the attack — make the program print the congratulations message with no password — you must feed it the raw bytes of a memory address. Most address bytes are not characters you can type (and some are 0x00), so you build the bytes in a file and feed the file to the program. On x86-64 an address is stored little-endian (low byte first): for example the placeholder address 0xdeadbeef is the eight bytes ef be ad de 00 00 00 00.

Why a file, and not a command-line argument? A command-line argument is a NUL-terminated string, so it can never contain a 0x00 byte — the argument would be cut off there. The shell's $(…) substitution also silently drops NUL bytes and trailing newlines. Since addresses contain 0x00 bytes, overflow payloads are fed through standard input (from a file), not as arguments.

Writing a binary file

Use printf: each ordinary character stands for itself, and each raw byte is written as \xHH (two hex digits). For example, to write four 'A' bytes followed by the placeholder address 0xdeadbeef as an 8-byte little-endian value:

printf 'AAAA\xef\xbe\xad\xde\x00\x00\x00\x00' > myfile

Here AAAA are four 0x41 bytes and \xef\xbe\xad\xde\x00\x00\x00\x00 is the address written one byte at a time, low byte first. printf adds no trailing newline, so the file holds exactly these bytes. (This is only an illustration — for the attack you supply your own padding length and the address you found in Q8.)

Reading (inspecting) a binary file

You cannot usefully cat a binary file — the unprintable bytes turn into garbage. Use xxd, which shows the bytes in hex on the left and as ASCII on the right. xxd myfile prints:

00000000: 4141 4141 efbe adde 0000 0000            AAAA........

The four 0x41 ('A') bytes, then the little-endian address, are exactly what you wrote. (Non-printable bytes show as . on the right.)

Feeding the file to the program

Put your crafted bytes in a file (say bad_input), then redirect it into the program's standard input with <:

./exampleoverflow < bad_input

If your bytes are right, the program prints

Congratulations! You have earned lots of $$$

even though you never typed the password — you hijacked its control flow.

A note on gets() and newlines. gets() reads until it sees a newline (0x0a) or the end of the input, and it is happy to read 0x00 bytes along the way. A file written by printf as above contains no newline, so every byte is read. Just don't put a stray newline in the middle of your payload, or gets() will stop early.
